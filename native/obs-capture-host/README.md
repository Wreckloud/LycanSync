# LycanSync OBS capture host (development migration)

This Windows x64 development host pins libobs to **OBS Studio 32.2.2**. An unpackaged Windows build can opt into it by setting `LYCANSYNC_OBS_CAPTURE_HOST`, `LYCANSYNC_OBS_WIN_CAPTURE_MODULE`, and `LYCANSYNC_OBS_WIN_CAPTURE_DATA` to absolute paths for the host executable, official `win-capture.dll`, and its module data directory. Monitor and ordinary-window video use OBS for all four presets, including changes during a session. No capture failure selects another engine. This video-only development path does not yet support screen audio or remote control. It is not included in the installer; the installed production path remains Rust until migration acceptance.

OBS renders a fixed 1920×1080 canvas at the requested 30, 60, or 120 FPS. Economy's 1280×720 output and text/motion hints reuse the existing page and sender configuration; economy does not lower the native texture dimensions. An in-session FPS change uses `obs_reset_video`, retaining the source, three texture slots, capture process, session ID and page track. Rendering pauses briefly during reset, rather than running permanently at 120 FPS and discarding frames. Success is acknowledged only after applying the change. A rejected reset attempts the previous native video configuration; failed recovery or an uncertain three-second request timeout ends capture, with no silent fallback or retry. The old fixed-profile capability flag and rejection path have been removed. No audio/remote-control retention claim is made before those OBS integrations exist.

For monitors the host loads the official `win-capture` module. Ordinary windows use a small OBS input-source adapter over the same version's official `libobs-winrt.dll`, binding its window API to the selected HWND instead of the plugin's title/class/executable rematching. The existing Rust source registry reserves that window's instance marker in its existing video session without starting a capture worker. The marker stays alive across source-list refreshes. Only the helper, main process and native host receive the identity tuple; it is not exposed to the page or diagnostic report. The host validates the marker before creating capture and before delivering frames; a closed or replaced window ends capture, never selects another window or monitor. Minimized/hidden windows use the existing suspension notification and placeholder path. The main process confirms OBS has stopped before releasing Rust's reservation; unconfirmed termination keeps the reservation and blocks another start. No second video engine runs for this reservation.

WinRT capability checks run on libobs's existing MTA graphics thread, not its STA main thread. Hiding the cursor/border requires the corresponding OS capability; a requested unsupported/denied borderless mode explicitly fails. No whole-monitor crop or automatic bordered fallback is used. Window mode does not initialize the `win-capture` plugin's game-hook updater. This is not a game-capture or universal borderless-compatibility claim.

The host copies OBS's rendered main texture into three bounded BGRA shared GPU texture slots and writes frame events to stdout. It skips delivery while the source still reports zero dimensions, rather than treating an initial empty canvas as its first source frame. Each NT texture has a keyed mutex; the producer finishes its D3D11 event query and releases the mutex before announcing the handle. It does not read the texture back to CPU memory. The parent process must validate the spawned executable identity before duplicating any announced texture handle.

Each slot remains busy until the parent sends `release:<slot-index>` after Electron releases all imported references. If all three slots are busy, the host drops the current update instead of allocating more textures or building an unbounded queue. The frame event includes the session ID, slot index, NT handle, dimensions, monotonic timestamp, delivered count, and dropped count. These are protocol messages, not disk logs. Existing low-frequency diagnostics sampling sends `diagnostics:<request-id>` to read current counters even when no new frame can leave the host; concurrent requests share one pending response, with a bounded timeout and session checks. libobs warning/error logs go to stderr, never the JSON protocol channel.

The production preload uses one session-owned OffscreenCanvas to snapshot an imported VideoFrame before forwarding it to the generated track. On the tested Windows/Electron 44.2.0 path, directly feeding the external frame to MediaStreamTrackGenerator stalls video playback, even without LiveKit. A canvas snapshot separates the consumer's frame ownership from the external texture; there is no direct-path fallback, extra capture source or per-frame readback API. This adds a canvas conversion and is not a zero-copy claim. Chromium chooses its acceleration path, so resource cost still requires comparison. The source frame/import is released by preload, the transferred snapshot by the page, and the scratch canvas on matching stop/error/suspension; a late old-session result cannot clear a new canvas.

Build with `build.ps1` below. The official Windows runtime ZIP does not include a development package: this script prepares a project-local binary SDK from the verified runtime and matching public headers, and generates `obs.lib` from the actual DLL exports. It does not create a fake upstream CMake package or rebuild the complete OBS application. The old external `find_package(libobs)` setup and the earlier ad hoc direct-compiler check are not alternative supported build paths.

At runtime, pass the corresponding official `win-capture.dll` path, its module data directory, the selected monitor device name, the cursor-capture setting, a per-run session ID, and an absolute module-config directory. Electron owns the latter under its user-data `obs-capture/32.2.2` directory; tests use their isolated profile or build-cache directory. The host normalizes the module path to forward slashes before libobs extracts its name, keeping writable plugin caches outside runtime dependencies. The host checks that the monitor still exists and sets the plugin's `monitor_id`; opaque source IDs are not monitor indices. Both the headers at compile time and `obs_get_version_string()` at startup must match 32.2.2. The manager sets the child's working directory to `bin/64bit`, because the official libobs binary locates effect files under `../../data/libobs`. The JavaScript manager is included because the main process imports it; native installer integration remains gated on migration and release acceptance.

Commands on stdin are line based; `shutdown` stops the output and EOF follows the same cleanup path. The manager allows four seconds for normal libobs cleanup, then requests termination and waits up to another 1.5 seconds for confirmed closure. This grace period does not restore revoked frame-delivery permission. If the process crashes, Windows releases its handles and the parent must invalidate the texture session when it observes child exit. Unconfirmed termination is an error: the manager keeps the process identity and blocks another start until closure is confirmed. The main process also retains the video session if cleanup after a failed start is unconfirmed, so another source cannot bypass that block. A stalled stdin write does not delay the shutdown deadline, and a late startup event cannot complete a start after stopping has begun.

The CLI arguments are module path, module data path, source kind (`monitor`/`window`), target (device name/HWND decimal string), capture-cursor flag, hide-border flag, session ID, config path, target FPS (`30`/`60`/`120`), window property name and property value (empty for monitors). Rebuild host, Rust helper and client together; the previous positional CLI is not supported. `configure:<request-id>:<fps>` applies a change and responds with `captureConfigured` or `captureConfigurationRejected`, carrying the same request/session IDs and the actual retained FPS. Stopping or process exit rejects an outstanding request; stale acknowledgements cannot complete a newer request.

The agreed migration is to complete window capture, all four quality presets, screen audio, and remote-control association before one cutover removes the replaced Rust video path. There will be no permanent dual-engine selection or failure fallback. The current prototype has not completed that replacement.

## Build and prepare without running capture

Run from the repository root in Windows x64 PowerShell with existing Visual Studio C++ Build Tools, its CMake component, and Windows SDK:

```powershell
./native/obs-capture-host/build.ps1
# After both official archives have been cached, rebuild without network access:
./native/obs-capture-host/build.ps1 -Offline
```

The script does not install tools, run the host/client/helpers, enumerate sources, or connect to a room. Downloads, extracted files, SDK headers/import library, and CMake outputs stay in the ignored `release/build-cache/obs-32.2.2` directory. A missing tool, invalid archive hash, unexpected DLL version/export table, build failure, or missing static DLL dependency is an error, not a fallback to the installed OBS.

The development output is `release/build-cache/obs-32.2.2/prepared`: `bin/64bit` contains the host and required runtime DLLs, `obs-plugins/64bit` contains only `win-capture`, and `data` retains core effects and the official plugin files. No OBS UI, Qt, browser, recording output plugin, or automatic installer integration is included. `build-manifest.json` records archive hashes, compiler toolset, runtime file hashes/size, and direct/delay import resolution against this computer's Windows files. Static import inspection does not validate dynamically loaded modules, OS/driver compatibility, or actual startup. The output still relies on the existing Windows/VC++ runtime; clean-machine installation remains unverified.

This is a local development bundle, not a release-ready redistribution. It includes the OBS GPL license and references the complete matching source archive, but third-party dependency licenses/corresponding source and final distribution materials still need review. The manifest keeps `redistributionReady: false`.

## Before any runtime test

The official `win-capture` module has broader initialization side effects than the selected source: its `obs_module_load` invokes `init_hook_files`, initializes game-capture helpers, and can update files under `%ProgramData%/obs-studio-hook` and Vulkan implicit-layer registry entries. Keeping the OBS application installation untouched does **not** imply that running this module is system-neutral. A monitor-only session still loads this module. The build workflow does not run these operations; runtime testing needs explicit permission covering them. Do not remove required files to suppress those effects, modify the upstream binary, or claim that only a private folder can be affected.

Further acceptance concentrates on common windows/games and eventual encoding/network delivery. The minimum B1 device/resource checks permit continued migration development; exhaustive hardware and long-running pressure tests are not prerequisites for every batch. Successful compilation or a bundle-size total still does not establish performance gains or release readiness.
